# GitHub-native releases: assets on Releases, links on Pages, no R2

Status: draft for review · 2026-10-29

## 1. Why

Every artifact the fork ships today lives in a Cloudflare R2 bucket behind
`nastech-assets.nastechresearch.workers.dev`: desktop installers, the
electron-updater feed, the Termux APT pool, the upstream toolchain mirror and
its build-input archive. That is a second hosting account to maintain, a second
thing to pay for, and a set of URLs that are neither the repository's own nor
discoverable from it.

The owner's decision: **GitHub is the only host.** Binaries on published GitHub
Releases, the site and human-facing links on GitHub Pages, nothing on
Cloudflare.

Two facts make this cheap rather than a rewrite:

- `apps/desktop/electron-builder.config.cjs` already falls back to
  `{ provider: 'github', owner, repo, channel }` whenever the R2 public URL is
  unset. Removing the R2 variable flips the updater; no feed rewrite is needed.
- Release assets are **not git objects**. They are stored by the release, so
  repository size and `git clone` size are unaffected by how many builds run.
  What grows is release storage, which section 5 bounds.

## 2. Decisions (fixed)

| Question | Decision |
|---|---|
| Where do binaries live | **Published GitHub Releases.** Pages keeps the site, docs, installers and download pages. |
| Termux | **Keep `pkg`.** A fixed-tag `termux-repo` release is the apt repository: index plus the current and previous `.deb`, refreshed on every publish. Signed with the existing `TERMUX_APT_GPG_KEY`. |
| Publication | **Stable publishes as a normal release** (resolves `latest`). **Canary publishes as a pre-release** (never `latest`). Drafts exist only while a build is in flight. |
| Canary retention | **Newest 3 stay**; older pre-releases are deleted with their assets at the start of each publish. |
| Commit builds | **Artifact only** — no release at all, retention-bounded. |
| Upstream toolchain mirror | A dedicated **`toolchain` release**, assets named by sha256. `pm`'s integrity and offline paths are unchanged. |
| Signing | Unchanged: unsigned by default, signed lanes skip when their configuration is absent. |

## 3. Target architecture

### 3.1 Release shape

- **Stable** — tag `vX.Y.Z`, normal release. Assets: `dmg`, `zip`, `blockmap`,
  `exe`, `msix` (where built), the Termux `.deb`, `latest.yml`, and the
  blockmaps electron-builder uploads with it. This release is the only thing
  `releases/latest` and the updater's default channel resolve to.
- **Canary** — tag `vX.Y.Z+canary.<stamp>`, `prerelease: true`. Same asset set,
  with `canary.yml` instead of `latest.yml`. Never `latest`.
- **Commit build** — no release. The bundle is a workflow artifact with a
  7-day retention. The recorded sizes (`bundle-artifact-sizes.json`) are what
  make a release measurable instead of estimated.
- **`termux-repo`** — one fixed-tag release holding the apt repository:
  `Packages`, `Packages.gz`, `Release`, `InRelease`, and the current and
  previous `.deb`. Its assets are **replaced**, not appended; it is the single
  deliberate exception to asset immutability, because `pkg` needs a stable
  source URL.
- **`toolchain`** — one long-lived release, one asset per tool sha256. Written
  by a maintainer job, not by app builds.

### 3.2 Update feed

`electron-builder`'s `publish` becomes unconditionally
`{ provider: 'github', owner, repo, channel }`. The `publicUrl` branch and the
`CLOUDFLARE_R2_PUBLIC_URL` input are deleted. electron-builder generates
`latest.yml` / `canary.yml` and their blockmaps as release assets, and
`electron-updater` reads them through the GitHub provider.

`apps/desktop/update-feed.cjs` keeps its URL canonicalisation for the
git-checkout update path; its generic/R2 branch is removed.

### 3.3 Installers and download pages

`install.sh` and `install.ps1` stop naming an asset host. They resolve the
current release in this order:

1. `https://nastechresearch.github.io/nastech-agent/latest.json` — a small file
   published at release time (tag, asset names, sizes, sha256),
2. the GitHub API `releases/latest` as a fallback,
3. an explicit `--tag` / `-Tag` argument, which skips both.

Pages additionally gets a human download page per platform that links to the
release asset. Nothing on Pages carries a per-file asset URL that a human has to
keep up to date; `latest.json` is generated by the publish job, never edited.

Serving `latest.json` from Pages is deliberate: installers read it from a
static file instead of spending the unauthenticated GitHub API budget
(60 requests/hour/IP) that a popular install link would exhaust.

### 3.4 Termux: `pkg` keeps working, served from a release

The apt source points at one fixed tag, so nothing on the user side changes:

```
deb https://github.com/nastechresearch/nastech-agent/releases/download/termux-repo/ ./
```

apt resolves `Release`/`InRelease`/`Packages.gz` relative to that base and then
downloads each `Filename:` from the same place; release-asset URLs are exactly
`<base>/<asset>` and apt follows the redirect to GitHub's object store.

Each publish refreshes that release in a fixed order:

1. upload the new `.deb`,
2. regenerate `Packages` / `Packages.gz`, sign `Release` → `InRelease` with
   `TERMUX_APT_GPG_KEY`, upload them **last**,
3. delete the assets for versions older than the previous one.

Ordering is the whole point: an index is only visible after the file it names
exists, which is exactly the failure the last run hit
(`404 … nastech-agent_0.21.5~canary…_aarch64.deb`). A client that reads mid-swap
sees either the old complete index or the new complete index, never a dangling
one.

`stage_apt_repo.py` keeps its index-building logic and changes only its
destination (release assets instead of R2 objects). The R2 upload and the
separate key-materialisation step are replaced by the ordered refresh above.

### 3.5 Toolchain mirror and build-input archive

- `pm/artifact-mirror.json` becomes
  `{"origin": "https://github.com/nastechresearch/nastech-agent/releases/download/toolchain", "prefix": ""}`
  so `artifact_mirror.py` resolves `<origin>/<sha256>` unchanged.
- `scripts/ci/archive_inputs.py` and `.github/workflows/archive-inputs.yml`
  upload workflow artifacts instead of R2 objects. Archives are build
  provenance, not product, so retention follows artifact retention.

### 3.6 What is deleted

- The `assets-worker` Cloudflare worker from the owned-asset registry and its
  two source files.
- Every `CLOUDFLARE_R2_*` input, secret and variable once nothing reads them.
- R2 upload/download steps in `desktop-bundled-release.yml`,
  `canary-release.yml`, `stable-release.yml`,
  `stable-release-publication.yml`, `desktop-bundle-smoke.yml`,
  `install-e2e-macos-run.yml`, `install-e2e-windows-run.yml`, `termux-verify.yml`.

## 4. Migration sequence

Each step is independently revertable and lands as its own engine PR; the fork
picks a step up with the next candidate.

0. **Prerequisite.** Fix `stable-release-publication`'s `reconcile` failure:
   `scripts/releases/sequencer.py` raises `Stable claim owns multiple workflow
   runs` as soon as one claim is attached to two dispatch runs, so a single
   failed attempt bricks every later one. Nothing can publish until a second
   dispatch is safe.
1. **Toolchain release.** Create the `toolchain` release, upload the current
   tool assets named by sha256, switch `artifact-mirror.json`. Verify `pm`
   installs with the R2 host blocked.
2. **Attach and publish, dual-writing.** The publish job uploads every asset
   to the release *as well as* to R2, then publishes: stable as a normal
   release, canary as a pre-release, commit builds as artifacts only. The
   retention sweep (keep newest 3 canaries) is the first step of that job. R2
   keeps receiving the same bytes until step 7, so either host can serve a
   download while the rest of the migration lands.
3. **Updater to GitHub.** Drop the `publicUrl` branch. Verify a built app's
   `app-update.yml` names the github provider and updates from a published
   canary.
4. **Installers and Pages.** `latest.json` published by job 2, installers
   resolve it, download pages generated.
5. **Termux.** Move the apt repository onto the `termux-repo` release with the
   ordered refresh; keep the existing `deb …` source line working unchanged.
6. **Archive inputs.** R2 → workflow artifacts.
7. **Decommission.** Delete the worker from the registry, remove the R2
   secrets/variables, and (owner action, outside the repo) delete the bucket
   and worker.

Steps 2–4 must land before 7: until the release carries every asset, removing
the R2 uploads would break a download path that still has users.

## 5. Storage and retention

- Release assets are not in git. Clone size and repository size are unchanged
  by any number of builds.
- Stable releases: permanent.
- Canary: newest **3** kept; older releases deleted with assets at the start of
  each publish. With six desktop targets (macOS ×2, Windows ×2, Linux ×2) plus
  the Termux `.deb`, a release is larger than a single platform; the measured
  number from `bundle-artifact-sizes.json` decides whether three canaries is
  still the right count or should drop to two.
- `termux-repo`: two `.deb` versions at all times, refreshed in place.
- Commit builds: artifacts only, 7-day retention, never a release.
- Toolchain: one release, grows only when a tool version is added.

## 6. Risks

| Risk | Handling |
|---|---|
| Release assets are immutable; a re-cut cannot overwrite one | Each build has its own tag; re-cutting a stable version means a new patch tag, stated in the release SOP |
| 2 GiB per-file limit | Current bundles are far below it; the publish step rejects a file over the limit loudly rather than truncating |
| Pages 1 GB site cap | Pages carries only text: site, docs, `latest.json`, installers. No binary ever goes there |
| `latest` can point at a canary | Canary is a pre-release, so `releases/latest` cannot resolve to it; a check asserts the flag on every canary publish |
| Installers hit the API rate limit | `latest.json` on Pages is the primary path; the API is only a fallback |
| Deleted canary breaks someone's saved link | Retention is documented where canary downloads are offered; stable links never move |
| The `termux-repo` release is mutable by design | Only the index and the two current `.deb` files are replaced, always in the order above, and nothing else references that tag |
| R2 and Releases both live during migration | Step order keeps every consumer on R2 until its replacement is verified; step 7 removes R2 last |

## 7. Verification

- `gh release view <canary>` → `prerelease: true`, assets present,
  `gh release view --json isLatest` is not it.
- `gh release view <stable>` → published, assets present, resolves as `latest`.
- Built app's `app-update.yml` names `provider: github`.
- `install.sh --dry-run` and `install.ps1 -DryRun` resolve the asset from
  `latest.json` with the R2 host blocked.
- `pm` install with the R2 host blocked.
- A grep gate: no `workers.dev`, `r2.dev` or `cloudflarestorage` outside test
  fixtures and this spec.
- Retention: after two canary publishes, exactly three canary pre-releases exist.
- Termux: `pkg update && pkg upgrade nastech-agent` installs the new version from
  the release-hosted repo, with the R2 host blocked.

## 8. Out of scope

- Renewing or provisioning Apple/Azure signing credentials.
- The Algolia search index.
- Anything in the 80-odd upstream tracker links.
